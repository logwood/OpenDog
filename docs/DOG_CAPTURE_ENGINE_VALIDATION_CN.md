`01_dog.mp4` 拍的是一个人和一只小狗在玩：狗脸小、运动快，画面里一直有人脸。它不是抓拍场景，而是**压力测试**，
用来看会不会误拍、引导提示是否合理。

## 1. 自动化测试

`pytest src/Pet-ReID-IMAG/tests/test_dog_engine*.py`：68 项通过。覆盖配置校验、Umeyama 对齐（多种尺度与旋转）、
姿态的旋转不变性与眼序规范化、视角去抖、One-Euro 滤波、ByteTrack（跳帧、低分延续、两只狗、过期）、质量排序与拒绝、
关键点可见度门控、三种抓拍策略、驻留确认前的暂存、top-k 多样性、两只狗不混用、物种门控（含头部裁剪阈值）、
方向搜索与关键点转正、相册模式、时间戳策略、非法输入、引导防抖、主目标粘性；ONNX 方面用常量输出图验证 YOLO-pose
（含端到端导出格式）、YOLOv5-face、SCRFD、YOLOX 的坐标还原，并通过真实 ONNX Runtime 会话跑完整流水线；I/O 方面覆盖
视频 PTS、坏图片、输出不覆盖、实时丢帧与异常上抛，以及 CLI 全流程（结果 JSON、三视角图片、复核页、逐帧日志、预览视频）。
v0.x 原有测试：48 项通过，4 项因本地专有资产缺失跳过，与改动前一致。

## 2. 导出与解码

- AnyFace 导出（`tools/export_anyface_onnx.py`）：本机没有真实权重，因此用随机初始化的 YOLOv5n-face（3 个检测层）和
  YOLOv5l6-face（4 个检测层，即 AnyFace 的结构）验证。ONNX Runtime 与 PyTorch 输出的最大差分别为 1.8e-4 和 1.2e-4，
  输出形状为 `[1, 6300, 16]` 和 `[1, 9180, 16]`，引擎能正常解码。新工具按模型实际的检测层数重建 `anchor_grid`
  （原 `export.py` 写死为 3 层，不适用于 4 层的 l6）。
- Ultralytics 真实导出：`output0 [1, 23, 3549]`，元数据带 `kpt_shape=[6,3]` 和 `kpt_names`，与解码器一致；在验证图上目视检查了框和关键点的位置。

## 3. 清晰度标定（真实犬脸）

用 `tools/calibrate_dog_quality.py`，在 300 张验证集近正脸（眼距 ≥ 40 px）上测量：先按 PetFace 模板对齐，再与人为加的
失焦、运动模糊比较。最终常数为 `LAPLACIAN_REF=80`，Crete 区间 `0.30–0.70`，`min_sharpness=0.15`。

| 条件 | 清晰度 P10 / P50 / P90 | 被判模糊 | 原图得分更高 |
|---|---|---:|---:|
| 原图 | 0.32 / 0.67 / 0.97 | 3% | — |
| 失焦 σ = 0.03 倍眼距 | 0.015 / 0.022 / 0.081 | 96% | 100% |
| 失焦 σ = 0.06 倍眼距 | 0.012 / 0.013 / 0.016 | 100% | 100% |
| 运动模糊 0.15 倍眼距 | 0.024 / 0.067 / 0.236 | 75% | 100% |
| 运动模糊 0.30 倍眼距 | 0.018 / 0.034 / 0.161 | 88% | 100% |

初始常数（`120`、`0.22–0.62`、`0.20`）会把 10% 的清晰原图判为模糊，所以按实测重新标定。
Stanford Dogs 里本身有压缩和失焦的照片，3% 的原图被拒里有一部分本来就不清晰。

## 4. 物种门控（YOLOX）

| 输入 | 结果 |
|---|---|
| 人像、猫、咖啡杯、马（整图） | 均无狗框 |
| 验证集整张狗照片 200 张 | 92% 有狗框 |
| 验证集脸框外扩 1.5 倍的头部裁剪 183 个 | 分数 ≥ 0.3：81%；≥ 0.5：72% |
| 猫的头部裁剪 | 被判为狗，得分 0.44 → 因此头部复核单独使用 0.5 阈值 |

v1 引擎、相册模式、四张非狗图：关闭门控时，早期学生模型把宇航员的人脸当成“正面狗脸”收进结果；
开启门控后，人、猫、杯子都被判为“不是狗脸”，马判为“未检测到狗脸”，一张都没有采集。
YOLOX-nano 在 20 张狗照片上检出 18 张，平均 IoU 0.78；YOLOX-tiny 检出 20 张，平均 IoU 0.82，因此默认用 tiny。

## 5. 学生模型（YOLO11n-pose，dog-face6）

- 结构：YOLO11n-pose（2.66M 参数），从 COCO-pose 预训练开始训练，6 个关键点（双眼、鼻尖、下巴、双耳根），带可见度。
- 数据：dog-pose 训练集 6773 张、6381 张脸。眼睛由 DogFLW 46 点模型在真值脸框上补标（第 6 节配方），
  7987 个实例中 5834 个通过“教师鼻子与真值鼻子相距不超过 0.6 倍眼距”的校验，共写入 9926 个眼睛标签。
  教师在强侧脸上不可靠，这些眼睛留作未标注。
- 训练：本机 CPU，320 输入，batch 32，12 轮，用时 1.2 小时（多数时间与其他测量共用 CPU）。权重 SHA-256 `988506c6…`，没有提交到 Git。
- Ultralytics 在验证集（1703 张图、1606 张脸，训练时没见过）上的结果：

| | 精确率 | 召回率 | mAP50 | mAP50-95 |
|---|---:|---:|---:|---:|
| 脸框 | 0.863 | 0.914 | 0.905 | 0.469 |
| 关键点（OKS） | 0.890 | 0.938 | 0.931 | 0.791 |

关键点的真值中，鼻、下巴、耳根是人工标注，眼睛是教师伪标签，所以关键点指标里有一部分是在衡量“学得像不像教师”。

## 6. 与 v0.x 级联的对比（同一验证子集，每 4 张取 1 张，共 426 张）

`tools/evaluate_dog_face_detector.py`。延迟在空闲的 4 核 CPU 上测量，包含预处理、推理和解码。

| 检测器 | 脸框召回 / 精确（IoU≥0.5） | 真值鼻子命中 | 鼻误差 P50（脸框尺寸） | 眼误差 P50（眼距，对比教师） | 延迟 P50 / P90 | 体积 |
|---|---|---:|---:|---:|---|---:|
| v0.x DogFLW 三模型级联 | 0.218 / 0.350 | 46% | 0.128 | 不适用（它本身就是教师） | 74.7 / 229.3 ms | 33.4 MB |
| 学生 320 FP32 | 0.904 / 0.852 | 92% | 0.047 | 0.127 | 10.6 / 12.8 ms | 10.9 MB |
| 学生 416 FP32 | 0.901 / 0.835 | 93% | 0.049 | 0.121 | 14.1 / 17.2 ms | 10.9 MB |
| 学生 416 FP16 | 0.901 / 0.835 | 93% | 0.049 | 0.120 | 15.6 / 19.4 ms | 5.5 MB |
| 学生 416 INT8（只量化卷积） | 0.904 / 0.844 | 93% | 0.048 | 0.132 | 21.0 ms | 3.2 MB |

“真值鼻子命中”指在真值鼻子 0.2 倍脸框尺寸范围内有预测的鼻子，不受各模型脸框定义不同的影响。
旧级联的框比真值脸框大，所以它的 IoU 召回偏低，主要应参考鼻子命中率。旧级联对鼻子的定义（鼻垫中心）也和真值（鼻尖）不同，
这部分差异同样计入了它的误差。学生模型是在同分布数据上训练的，比较对它有利；跨数据集的对比需要用你自己的视频再做一次。
旧级联的 P90 偏高，是因为它重新定位时会尝试多个 90° 方向。

## 7. 端到端运行

**相册模式，280 张没见过的验证照片**（每张是不同的狗，只用来检验每张照片的判定）：249 张检出狗脸，其中 164 张通过质量门槛
（高 40、中 54、低 70）。不通过的原因：脸太小 37、眼睛或鼻子被遮挡 29、模糊 13、鼻子位置不合理 3、眼睛无法分辨 2、过暗 1。
另有 32 张脸被物种门控拒绝。每张照片 P50 38 ms。三个视角的最终选图（见下）经过人工查看：正面是睁眼、清晰的正脸；
左右两张都是真正的侧转（显示角度约 ±29°）。

本节在测量过程中发现并修复了三个问题，均已补充测试：
1. 相册模式误用了 hybrid 策略。照片之间按 1 s 计时，2 s 的改进窗口导致看到第二张照片后就锁定，第一次选出的正面是闭眼、被爪子挡住的狗；
   改为相册始终用 best 策略后，选出的是睁眼的清晰正脸。
2. 鼻尖模型的 yaw 线索约是鼻垫中心的 1.9 倍，套用原来的视角带时，“侧面”实际只是轻微转头；按格式换算 `yaw_scale` 后已修正。
3. 鼻子位置的合理范围 `[0.10, 1.60]` 会误拒 7.6% 的真实标注脸（长嘴犬低头时比值可达 2）；按 4963 张标注脸的分布放宽到 `[0.05, 2.20]`。

**非狗图片**：开启门控时，宇航员、猫、咖啡杯被判为“不是狗脸”，马判为“未检测到狗脸”，一张都没有采集；
关闭门控时，宇航员的人脸被当成“正面狗脸”收进结果。YOLOX-nano 和 YOLOX-tiny 的结果相同。

**压力视频 `01_dog.mp4`**（小狗快速运动，人脸一直在画面里）：

| 版本 | 结果 |
|---|---|
| 修复前 | 自动方向搜索在没有脸的每一帧都切换方向，四分之三的帧是转着分析的，物种门控也就看不到狗；引导在“没有狗脸”和“模糊”之间来回跳 |
| 修复后（每 10 帧最多试探一次） | 289 帧全部按 0° 分析；266 帧提示“看到狗狗了，但脸太小或没有对着镜头”，18 帧提示“未检测到狗脸”；没有采集任何低质量图片 |
| 远距离兜底 | 在狗身裁剪上能找到狗头，但多为侧脸或背脸且有运动模糊，得分 0.18–0.48，低于建轨迹所需的 0.55，所以不采集，这是对的 |
| v0.x 级联（同一视频，v1 引擎调用） | 同样没有采集；每帧 145–195 ms |

**实时与稳定性**：
- 逐帧分析 30 fps 的压力视频，整条流水线 P50 17.7 ms / P95 41.2 ms，引擎自身开销 P50 0.12 ms / P95 0.21 ms。
- 按原速实时回放：289 帧中处理 284 帧，5 帧在队列里被新帧替换；从提交到出结果 P50 20.6 ms / P95 52.1 ms。
  P95 主要来自检测、远距离兜底和门控刷新恰好落在同一帧的情况。
- 同一进程里连续跑 4 遍真实视频（1156 帧）：0 个异常，常驻内存峰值 216 → 222 → 222.5 → 222.5 MB，结束后没有残留的轨迹和事件。
- 合成压测：3000 帧，狗进场、离场、两只狗同时出现，并夹杂上游的坏数据；轨迹数、上下文、事件和抓拍缓冲都没有超过上限。

## 8. FP16 / INT8

`tools/optimize_dog_onnx.py`：一半图片用于校准，另一半用于和 FP32 对比；最后再用标注真值评估（见第 6 节的表）。

| 模型 | 变体 | 与 FP32 相比：召回 / 精确 | 关键点偏差（眼距） | 体积 | x86 CPU 延迟 |
|---|---|---|---|---:|---:|
| 学生 416 | FP16 | 1.00 / 1.00 | 0.002 | 5.5 MB | 比 FP32 慢（FP16 面向 GPU / NPU） |
| 学生 416 | INT8，整图量化 | 0 / 0 | — | 3.3 MB | — |
| 学生 416 | INT8，只量化卷积 | 1.00 / 1.00 | 均值 0.067，P95 0.148 | 3.2 MB | 21 ms，FP32 为 14 ms |
| YOLOX-nano | FP16 | 1.00 / 1.00 | — | 1.85 MB | — |
| YOLOX-nano | INT8，只量化卷积 | 0.65 / 0.91 | — | 1.2 MB | — |

结论：
- GPU 或 NPU 用 FP16。x86 CPU 用 FP32。ARM / NNAPI / QNN 可以用学生模型的 INT8，前提是先在目标设备上测过延迟和关键点偏差。
- 门控不用 INT8，除非做量化感知训练（QAT）。
- 整图量化时，检测头把坐标（0–416）和得分（0–1）拼进同一个张量，共用一个 INT8 量化尺度，得分全部归零；
  工具已默认只量化卷积。原来 YOLOX 发布的 ONNX 是 opset 11，按通道量化前需要先升级到 opset 13，工具会自动处理。

**门控模型选择**（200 张验证照片，同一套脸框）：YOLOX-nano 3.7 MB，整图找到狗 86.5%，头部裁剪确认 69.9%；
YOLOX-tiny 20.2 MB，分别为 92% 和 71.6%，耗时约是 nano 的 4 倍。相册模式下换用 tiny，被拒的脸只从 32 张减到 27 张，耗时却翻倍（P50 74 对 37 ms）。
所以默认用 nano：门控按轨迹判断并会重试，视频场景能弥补它较低的单帧召回。

## 8.1 浏览器 H5 端到端（采集协议 dog-capture/1）

无头 Chromium + 由真实狗照片生成的 1280×720 / 30 fps 虚拟摄像头，H5 端 onnxruntime-web WASM 跑真实模型，
服务端复检也跑真实模型（识别模型用替身）：比对场景 1.96 s 选好正面 2 张，建档场景（左右必选）5.7 s
（受视频每侧 4 s 限制）；端上 10–15 fps；复检全部通过（与端上框 IoU 0.983–0.999，质量 0.84–0.91 / high）；
token 提交进入建档 / 比对；控制台零报错；WASM 运行时以 br 传输 2.8 MB。
详情和复现命令见 [`DOG_CAPTURE_PROTOCOL_CN.md`](DOG_CAPTURE_PROTOCOL_CN.md) 第 11 节。
