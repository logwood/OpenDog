# dog_capture v1 本机速度实测（2026-11-11）

**当前原生流程可以接近视频原帧率运行，但还未达到稳定、逐帧处理 30 fps 的水平。** 在用户视频上，交付环境 CPU 的完整实时延迟 P95 为 **64.34 ms**；本次修复后的 CUDA FP32 为 **68.32 ms**。GPU 在这段视频上没有形成明确的延迟优势。结果同时记录丢帧和运行间波动，不用单模型 FPS 代替实际体验。

本轮增加可复跑的测速工具，修复 CUDA 默认 TF32 导致的一处物种门控数值差异。CPU 仍为质量优先配置的默认后端。模型关键点、左右转和最佳照片的效果缺口仍见 [集成报告](DOG_CAPTURE_V1_INTEGRATION_CN.md)，本轮未将模型效果验收改为通过。

完整数值、模型/视频校验值、逐次结果、原始记录位置与哈希见 [速度数据](../assets/dog_capture/v1_reference/speed_report_20261111.json)。

## 测试条件与计时口径

- 本机：i9-13980HX，24 核 / 32 线程；RTX 4060 Laptop 8 GB；16 GB 内存；驱动 566.07；接电、Windows 平衡电源计划，其他桌面应用保持运行。没有修改系统电源或驱动设置。
- CPU 交付环境：Python 3.12.13、ORT 1.23.2、NumPy 2.5.4；同版本 CPU/CUDA 对照环境：ORT 1.26.0、NumPy 2.4.4。OpenCV 都为 5.0.0。主结果使用 ORT 4 线程、OpenCV 默认 32 线程。
- 人脸模型：用户的 `dog_face_pose.onnx`，输入 320×320，文件 10,845,283 字节；物种门控：YOLOX-nano，416×416，3,659,407 字节。两份 ONNX 均保持原始哈希和权重。
- 用户视频：720×1280，30 fps，43.8 秒，实际解码 1,314 帧。公开 Wolfhound：1280×720，24 fps，50.5 秒，实际解码 1,212 帧；容器声明 1,213 帧，测速按实际解码总数核对。
- 使用 `capture_quality.json`：物种门控开启、自动旋转、ROI 重检、跟踪、姿态、质量评分和 hybrid 选图全部开启，质量下限 `high`；完整播放，不因采齐视角提前退出。
- 独立模型测试：两段视频分别全片均匀取 24 帧、交替送入；每阶段预热 30 次，主结果计时 300 次。纯推理从预处理好的 CPU tensor 到返回 CPU 输出，包含 GPU 传输和同步；`detect` 额外包含图像预处理、解码和 NMS。
- 实时测试使用生产 `LatestFrameRunner`、容量为 1 的队列和视频 PTS。**表中的延迟从提交已解码帧到计算完成，包含排队，排除摄像头/驱动、页面绘制、网络和 Re-ID。** 解码、生产端迟到及从计划 PTS 到结果的耗时另存在原始记录中。
- 模型预热后计时，不把首次加载与稳态延迟混合。日志落盘、最终照片保存放在计时结束后；没有预览窗口。各测速进程串行运行。
- 两轮合并 P50/P95 从逐帧数据重新计算，**不是对两轮百分位取平均**。这是一次桌面工作负载下的实测，不是手机或 H5/WASM 的速度结果。

## 完整流程的实时结果

每项两轮完整回放。P50/P95 单位为毫秒。

| 后端 | 视频 | P50 | P95 | 各轮 P95 范围 | 丢帧 / 输入帧 | 丢帧率 |
|---|---|---:|---:|---:|---:|---:|
| CPU，ORT 1.23.2（交付环境） | 用户 30 fps | 17.18 | 64.34 | 51.24–75.06 | 170 / 2628 | 6.47% |
| CPU，ORT 1.26.0（同版本对照） | 用户 30 fps | 17.97 | 65.98 | 56.48–82.90 | 199 / 2628 | 7.57% |
| CUDA FP32，ORT 1.26.0（最终配置） | 用户 30 fps | 30.53 | 68.32 | 64.85–71.21 | 146 / 2628 | 5.56% |
| CPU，ORT 1.23.2（交付环境） | Wolfhound 24 fps | 18.08 | 66.83 | 64.53–72.25 | 107 / 2424 | 4.41% |
| CPU，ORT 1.26.0（同版本对照） | Wolfhound 24 fps | 19.13 | 56.90 | 53.00–65.93 | 80 / 2424 | 3.30% |
| CUDA FP32，ORT 1.26.0（最终配置） | Wolfhound 24 fps | 33.49 | 58.89 | 53.93–62.54 | 3 / 2424 | 0.12% |

CUDA FP32 的用户视频两轮实际处理约 28.52、28.08 fps；Wolfhound 约 23.93、23.99 fps。24 fps 输入的结果不能直接证明 30 fps 性能。容量为 1 的队列避免持续积压，但替换等待帧会丢失某些候选图像，因此丢帧率也是选图流程需要关注的指标。

交付环境 CPU 的离线逐帧吞吐为：用户视频 **39.27–52.00 fps**，Wolfhound **32.13–39.04 fps**，均处理全部帧。离线平均吞吐超过输入帧率，并不保证实时回放没有慢帧和丢帧。

## 慢帧与参数对照

追加物种检测、头部裁剪检查和 ROI 重检会放大慢帧。例如交付 CPU 在用户视频中，触发额外模型的帧，其计算 P95 为 **97.83 ms**；未触发这些额外模型的帧为 **38.96 ms**。因此需要同时检查推理次数、预处理和运行时调度，不能只压缩一次狗脸网络的耗时。

本轮也测了 CPU 1 / 8 线程、OpenCV 单线程、ORT 1.26.0 CPU，以及修改前默认 CUDA TF32：

- CPU 1 / 8 线程未显示可直接替换现配置的稳定优势；完整微基准留在 JSON 中。
- OpenCV 单线程的 CPU 用户视频实时 P95 为 96.58 ms、丢 214 / 1314 帧；该次测试没有改善用户视频。
- OpenCV 单线程的修改前 CUDA 两轮用户视频 P95 为 70.09 / 77.03 ms；独立模型测得更快，没有转化成稳定实时收益。
- 同版本 CPU 对照补齐后，仍没有证据表明只升级 ORT 即可解决用户视频的慢帧；没有据此升级默认运行环境。
- 修改前 CUDA TF32 的用户视频两轮 P95 为 27.04 / 65.62 ms，波动显著，且出现下述数值差异。它的较快成绩没有用作最终 CUDA FP32 配置的结果。

以上对照并非受控的系统调度或功耗根因实验，不能把运行间波动全部归因于某一个参数。本轮保持默认线程配置，先记录真实基线。

## CUDA 数值一致性修复

Profiler 分别确认狗脸和物种网络的计算节点实际在 CUDA 执行，未把 CPU 回退当作 GPU 成绩。测速会在请求的后端没有用于两个模型时失败。

修改前的 CUDA 默认 TF32 在 48 个全片采样帧中：狗脸检测均可匹配，关键点最大坐标差约 **0.1972 像素**；物种门控出现 **1 帧 CPU 有检测、GPU 没有检测**。原始输出的数值容差检查也未全部通过。

关闭 TF32 后，同一组采样帧的 34 个人脸检测和 34 个物种检测全部匹配；人脸关键点最大坐标差 **0.000244 像素**，物种框最大坐标差 **0.000469 像素**。最终配置重跑两段视频并再次通过这项检查；两个模型的原始输出抽样也通过 `atol=0.01, rtol=0.001` 对照。

因此 `dog_capture/engine/runtime.py` 的 CUDA provider 现在明确设置 `use_tf32=False`，并在运行报告中附带实际 provider options。它修复的是推理后端的数值差异；不会修复该参考权重本身的姿态/选图问题。

本轮没有构建或测量这份新 ONNX 的 TensorRT 引擎。旧 v0.x TensorRT 的数字没有混入本报告。FP16/INT8/TensorRT 的后续速度结果需要使用同一组完整视频并另做精度验收。

## 复现

从仓库根目录运行，每次使用一个新的输出目录。脚本不覆盖已有结果，也不在运行中自动安装依赖或修改系统设置。

```powershell
$speedInputs = @('--source', 'data/dog_capture/user/2611101816341481.mp4',
                 '--source', 'data/dog_capture/public/wolfhound_panting.ogv')
$speedTool = 'src/Pet-ReID-IMAG/tools/benchmark_dog_capture_v1.py'

# CPU：纯模型 + 离线完整视频 + 两轮原速回放。
& .tmp/dog-capture-v1-env/Scripts/python.exe $speedTool @speedInputs `
  --output "artifacts/runs/dog_capture/speed-cpu-$([guid]::NewGuid())" `
  --providers cpu --threads 4 --stage all --repeats 2 --verify-provider

# 本机已安装的 GPU 环境；最终 CUDA FP32：纯模型 + 两轮原速回放 + 数值核验。
& D:/CondaData/envs/torch312/python.exe $speedTool @speedInputs `
  --output "artifacts/runs/dog_capture/speed-cuda-$([guid]::NewGuid())" `
  --providers cuda --threads 4 --stage all --playback realtime --repeats 2 `
  --preload-cuda --verify-provider --verify-decoded
```

GPU 需要可用的 `onnxruntime-gpu` 和匹配的 CUDA/cuDNN DLL。`--preload-cuda` 在当前进程加载已有依赖，不改变系统 PATH。普通 CPU 环境不能仅靠传入 `--providers cuda` 变成 GPU 环境。按上述顺序运行，避免同时开两个测速进程。

每次输出包含 `summary.json`、每轮 `result.json`、逐帧 `timings.jsonl`、实际选中图像，以及开启核验时的 ORT profiler 文件。本次数值在 `artifacts/runs/dog_capture/v1_speed_20261111/`；摘要逐一记录原始文件哈希，并核对已读帧 = 已处理帧 + 丢帧，以及实际解码完整性。

相关 Python 回归 **83 项通过**；测速脚本编译与 CLI 帮助检查通过；新建 CUDA 会话返回实际 `use_tf32=0`。现有 Starlette/httpx 测试客户端的弃用提示不影响这些测试结果。

本轮沿用 `high` 质量要求：用户视频没有合格照片，Wolfhound 仍缺右侧。这项测速不改变效果验收结论。H5 显示/网络、手机真机、Re-ID 和完整三视角采集等待时间不在这张原生速度表内。
